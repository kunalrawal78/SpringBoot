# 3. Revision of Dependency Injection

Suppose we have:

```java
public class PaymentService {

    public void pay() {
        System.out.println("Payment Done");
    }
}
```

And:

```java
public class OrderService {

    private PaymentService paymentService;

    public void placeOrder() {

        paymentService.pay();

        System.out.println("Order Placed");
    }
}
```

`OrderService` depends on `PaymentService`.

Therefore:

```text
PaymentService = Dependency
OrderService   = Dependent
```

---

# 4. Problem with Manual Dependency Creation

One approach is:

```java
public class OrderService {

    private PaymentService paymentService =
            new PaymentService();
}
```

This works, but it creates a problem.

`OrderService` is now responsible for:

1. Handling orders
2. Creating `PaymentService`

This violates the **Single Responsibility Principle**.

The class should focus on orders, not dependency creation.

---

# 5. Dependency Injection

Instead of creating the dependency inside the class:

```java
new PaymentService();
```

we provide the dependency from outside.

### Constructor Injection

```java
public class OrderService {

    private PaymentService paymentService;

    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}
```

Now `OrderService` does not create `PaymentService`.

Someone outside provides it.

For example:

```java
PaymentService paymentService =
        new PaymentService();

OrderService orderService =
        new OrderService(paymentService);
```

This is:

> **Dependency Injection**

---

# 6. Inversion of Control

The previous example still requires us to manually:

- Create `PaymentService`
- Create `OrderService`
- Connect both objects
- Inject the dependency

The video asks:

> What if Spring does all of this for us?

This is where **Inversion of Control** comes in.

---

## IoC

**IoC = Inversion of Control**

Normally:

```text
Developer
   ↓
Creates Objects
   ↓
Connects Objects
   ↓
Manages Objects
```

With Spring:

```text
Spring
   ↓
Creates Objects
   ↓
Connects Objects
   ↓
Manages Objects
```

The control is transferred from the developer to Spring.

Hence:

> **Inversion of Control**

---

# 7. IoC Container

Spring Core provides an **IoC Container**.

The container is responsible for:

- Creating objects
- Managing objects
- Connecting dependencies
- Injecting dependencies
- Managing Beans

Previously our `main()` method was doing:

```text
Create PaymentService
        ↓
Create OrderService
        ↓
Pass PaymentService
        ↓
OrderService gets dependency
```

With Spring:

```text
IoC Container
      |
      ├── Creates PaymentService
      |
      ├── Creates OrderService
      |
      └── Injects PaymentService
             into OrderService
```

# 9. Beans

A very important Spring term is:

> **Bean**

A Bean is an object that is **created and managed by the Spring IoC Container**.

For example:

```text
PaymentService Object
        ↓
Managed by Spring
        ↓
PaymentService Bean
```

Similarly:

```text
OrderService Object
        ↓
Managed by Spring
        ↓
OrderService Bean
```

---

## Object vs Bean

```text
Object
  ↓
Any Java object

Bean
  ↓
Object managed by Spring
```

Therefore:

> Every Bean is an Object, but every Object is not necessarily a Bean.

# 11. Java Reflection API

Spring needs to inspect classes at runtime.

Java provides:

> **Reflection API**

Reflection allows a program to inspect class information at runtime.

For example:

```java
Class<Student> c1 = Student.class;
```

Here:

```text
Student.class
      ↓
Class object
      ↓
Metadata about Student
```

Reflection can provide information about:

- Class name
- Fields
- Constructors
- Methods
- Annotations
- Modifiers

---

## Why Spring Uses Reflection

Spring needs to discover information about classes.

For example:

```java
@Component
public class PaymentService {
}
```

Spring needs to know:

```text
Is this class a component?
What is its class?
What constructors does it have?
What dependencies does it need?
```

Reflection helps Spring inspect this information.

# 18. Dependency Injection by Spring

Suppose:

```java
@Component
public class OrderService {

    private PaymentService paymentService;

    public OrderService(PaymentService paymentService) {
```


```text
1. Creates PaymentService Bean
2. Creates OrderService
3. Passes PaymentService into OrderService
4. Dependency becomes injected
```

# 19. `@Autowired`

`@Autowired` tells Spring:

> **Inject the required dependency here.**

Example:

```java
@Autowired
private PaymentService paymentService;
```

# 20. Constructor Injection

Constructor injection means the dependency is provided through the constructor.

Example:

```java
@Component
public class OrderService {

    private PaymentService paymentService;

    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}
```

---

## Important Point

With a **single constructor**, Spring can perform constructor injection without explicitly writing:

```java
@Autowired
```

So this:

```java
public OrderService(PaymentService paymentService) {
    this.paymentService = paymentService;
}
```

is sufficient.

Conceptually:

```text
Constructor
    ↓
Spring sees dependency
    ↓
Finds PaymentService Bean
    ↓
Passes it to constructor
```

---

# 21. Setter Injection

Dependency can also be injected through a setter method.

Example:

```java
@Component
public class OrderService {

    private PaymentService paymentService;

    @Autowired
    public void setPaymentService(
            PaymentService paymentService) {

        this.paymentService = paymentService;
    }
}
```

The sequence is:

```text
Create OrderService
       ↓
Create PaymentService
       ↓
Call setter
       ↓
Inject PaymentService
```

The video explains that setter injection happens after the object has been created.

---

# 22. Field Injection

Dependency can also be injected directly into a field.

Example:

```java
@Component
public class OrderService {

    @Autowired
    private PaymentService paymentService;
}
```

Spring directly injects the dependency into the field.

Conceptually:

```text
Create OrderService
       ↓
Find PaymentService
       ↓
Inject into field
```

---

# 23. Comparison of Injection Types

| Type | Example | Main Idea |
|---|---|---|
| Constructor Injection | Constructor parameter | Dependency provided during object creation |
| Setter Injection | Setter method | Dependency provided through setter |
| Field Injection | Field | Dependency injected directly into field |

### Constructor Injection

```java
public OrderService(PaymentService paymentService) {
    this.paymentService = paymentService;
}
```

### Setter Injection

```java
@Autowired
public void setPaymentService(
        PaymentService paymentService) {

    this.paymentService = paymentService;
}
```

### Field Injection

```java
@Autowired
private PaymentService paymentService;
```

# 24. Multiple Beans of Same Type

Now consider an important situation.

Suppose:

```text
Payment
   |
   ├── CardPayment
   └── UpiPayment
```

Both implement:

```java
public interface Payment {

    void pay();
}
```

### CardPayment

```java
@Component
public class CardPayment implements Payment {

    @Override
    public void pay() {
        System.out.println("Paying via Card");
    }
}
```

### UpiPayment

```java
@Component
public class UpiPayment implements Payment {

    @Override
    public void pay() {
        System.out.println("Paying via UPI");
    }
}
```

Now:

```java
public OrderService(Payment payment) {
    this.payment = payment;
}
```

Spring sees:

```text
Payment
  |
  ├── CardPayment Bean
  └── UpiPayment Bean
```

Spring asks:

> Which Payment Bean should I inject?

This creates ambiguity.

---

# 25. `@Primary`

`@Primary` tells Spring:

> **Prefer this Bean when multiple Beans of the same type exist.**

Example:

```java
@Component
@Primary
public class CardPayment implements Payment {

    @Override
    public void pay() {
        System.out.println("Paying via Card");
    }
}
```

Now:

```text
Payment
  |
  ├── CardPayment ← @Primary
  └── UpiPayment
```

If Spring needs a `Payment` and no specific Bean is selected:

```text
CardPayment
```

will be selected.

---

## Important

`@Primary` does not remove the other Bean.

Both still exist:

```text
CardPayment Bean
UpiPayment Bean
```

But one is preferred.

---

# 26. `@Qualifier`

Instead of defining a default Bean, we can explicitly specify which Bean should be used.

Use:

```java
@Qualifier
```

Example:

```java
public OrderService(
        @Qualifier("upiPayment") Payment payment) {

    this.payment = payment;
}
```

Now Spring specifically selects:

```text
UpiPayment
```

---

# 27. `@Primary` vs `@Qualifier`

| `@Primary` | `@Qualifier` |
|---|---|
| Preferred/default Bean | Specific Bean |
| Used on Bean | Used at injection point |
| Spring automatically prefers it | Developer explicitly selects |
| Good for default implementation | Good when exact implementation is required |

### Easy way to remember

```text
@Primary
    ↓
"Prefer this"

@Qualifier
    ↓
"Use this exact one"
```

# 28. `@Bean`

So far we used:

```java
@Component
```

to tell Spring:

> Manage this class.

But Spring also provides another way:

```java
@Bean
```

`@Bean` is generally used inside a configuration class.

Example:

```java
@Configuration
public class AppConfig {

    @Bean
    public PaymentService paymentService() {
        return new PaymentService();
    }
}
```

Spring receives the returned object and manages it as a Bean.

---

# 29. `@Bean` Method

Consider:

```java
@Bean
public PaymentService paymentService() {

    return new PaymentService();
}
```

The method:

```text
paymentService()
```

creates the object.

Spring manages the returned object.

Flow:

```text
@Bean method
     ↓
Method executes
     ↓
new PaymentService()
     ↓
Returned object
     ↓
Spring manages it as Bean
```

---

# 30. `@Bean` with Interface Implementations

This becomes especially useful with interfaces.

Suppose:

```java
public interface Payment {

    void pay();
}
```

And:

```java
public class CardPayment implements Payment {

    @Override
    public void pay() {
        System.out.println("Paying via Card");
    }
}
```

We can configure:

```java
@Configuration
public class AppConfig {

    @Bean
    public Payment createCardPayment() {
        return new CardPayment();
    }
}
```

Now Spring manages the returned `Payment` object.

---

# 31. `@Bean` vs `@Component`

### `@Component`

```java
@Component
public class PaymentService {
}
```

Spring discovers the class through component scanning.

---

### `@Bean`

```java
@Bean
public PaymentService paymentService() {
    return new PaymentService();
}
```

Spring gets the object from the configuration method.

### Simple Difference

```text
@Component
     ↓
"Spring, manage this class."

@Bean
     ↓
"Spring, manage the object returned by this method."
```

# 36. `@Component` + `@Bean` Together

An important question:

> What happens if the same class has `@Component` and we also create its object using `@Bean`?

For example:

```java
@Component
public class CardPayment implements Payment {
}
```

and:

```java
@Configuration
public class AppConfig {

    @Bean
    public Payment createCardPayment() {
        return new CardPayment();
    }
}
```

At first glance, it may appear that Spring will create two Beans.

But the video explains that the configuration through `@Bean` gets priority for that object in this situation.

Conceptually:

```text
@Component
     ↓
Spring can create object

@Bean
     ↓
Configuration explicitly provides object

        ↓

@Bean configuration takes priority
```

The component can therefore be ignored for that same class/object configuration rather than producing two identical Beans.

---

# 37. Bean Creation Priority

The important concept from the video is:

> **Explicit Bean configuration has priority over automatic component creation when both target the same class.**

Conceptually:

```text
@Component
    ↓
Spring can create object

@Bean
    ↓
Developer explicitly provides object

@Bean
    ↓
Higher priority
```

Therefore, using both does not automatically mean:

```text
2 Beans
```

for the same configuration target.

# 38. Why `AppConfig` is Required

A natural question:

> Why do we need a separate `AppConfig` class?

We could technically put configuration directly inside `main()`.

But that makes the entry point complicated.

Without configuration separation:

```text
main()
 ├── Create context
 ├── Configure components
 ├── Configure Beans
 ├── Manage dependencies
 └── Start application
```

The `main()` method becomes responsible for too many things.

---

# 39. Configuration vs Main Method

The purpose of the configuration class is to separate:

```text
Application Logic
```

from:

```text
Spring Configuration
```

Therefore:

```text
Main
 ↓
Start Application
```

while:

```text
AppConfig
 ↓
Spring Configuration
```

Example:

```java
@Configuration
@ComponentScan("in.coderarmy")
public class AppConfig {
}
```

Then:

```java
ApplicationContext context =
    new AnnotationConfigApplicationContext(
        AppConfig.class
    );
```

This keeps the main method clean.

# 44. `ApplicationContext` vs `BeanFactory`

The hierarchy can be thought of as:

```text
ApplicationContext
       |
       ↓
extends / builds on BeanFactory functionality
       |
       ↓
BeanFactory
```

More specifically, `ApplicationContext` inherits BeanFactory-related capabilities through Spring's interface hierarchy.

Therefore, many BeanFactory operations are available through ApplicationContext.

---

## Why ApplicationContext?

Spring applications generally use:

```text
ApplicationContext
```

rather than directly interacting with:

```text
BeanFactory
```

because `ApplicationContext` provides a richer application-level container abstraction.

# 47. Interview Questions

## Q1. What is Dependency Injection?

Dependency Injection is a design technique where a class receives its dependencies from an external source rather than creating them itself.

---

## Q2. What is IoC?

IoC means the control of object creation and management is transferred from the developer to the Spring Framework.

---

## Q3. What is an IoC Container?

It is the Spring container responsible for creating, configuring, wiring, and managing Beans.

---

## Q4. What is a Spring Bean?

A Spring Bean is an object that is created and managed by the Spring IoC Container.

---

## Q5. What does `@Component` do?

It marks a class as a Spring component so that it can be detected during component scanning and managed as a Bean.

---

## Q6. What does `@ComponentScan` do?

It tells Spring which package(s) should be scanned for components.

---

## Q7. What does `@Configuration` do?

It marks a class as a source of Spring configuration.

---

## Q8. What is ApplicationContext?

`ApplicationContext` is a Spring interface representing the application-level IoC container.

---

## Q9. What is `AnnotationConfigApplicationContext`?

It is an implementation of ApplicationContext used for annotation-based configuration.

---

## Q10. What is `@Autowired`?

It tells Spring to resolve and inject a suitable dependency.

---

## Q11. What happens if multiple Beans of the same type exist?

Spring needs additional information to select one.

We can use:

```text
@Primary
```

or:

```text
@Qualifier
```

---

## Q12. What is `@Primary`?

It marks one Bean as the preferred Bean when multiple candidates of the same type exist.

---

## Q13. What is `@Qualifier`?

It explicitly specifies which Bean should be injected.

---

## Q14. Difference between `@Primary` and `@Qualifier`?

```text
@Primary
→ Default/preferred Bean

@Qualifier
→ Specific Bean
```

---

## Q15. What is `@Bean`?

`@Bean` tells Spring to manage the object returned by a configuration method.

---

## Q16. Difference between `@Component` and `@Bean`?

```text
@Component
→ Put annotation on class.

@Bean
→ Put annotation on configuration method.
```

---

## Q17. What is Reflection?

Reflection allows Java programs to inspect and interact with class metadata at runtime.

---

## Q18. What is a Bean Definition?

A Bean Definition is metadata that Spring uses to understand how a Bean should be created and managed.

---

## Q19. Why do we use a Configuration class?

To keep Spring configuration separate from the application's main entry point and business logic.

---

## Q20. What is BeanFactory?

`BeanFactory` is a Spring IoC container interface providing fundamental Bean-management functionality.

---

## Q21. What is the relationship between BeanFactory and ApplicationContext?

`ApplicationContext` is a higher-level container abstraction that extends/inherits BeanFactory-related functionality.

# 🔥 Final Concept

The entire lecture can be reduced to this:

```text
Developer writes classes
        ↓
Marks required classes/configuration
        ↓
@Component / @Configuration / @Bean
        ↓
@ComponentScan
        ↓
Spring finds classes
        ↓
Creates Bean Definitions
        ↓
Creates Beans
        ↓
Finds dependencies
        ↓
Resolves multiple Beans
        ↓
@Qualifier / @Primary
        ↓
Injects dependencies
        ↓
IoC Container manages everything
        ↓
Application uses the Beans
```

> **Core idea:** Spring takes responsibility for creating and managing application objects and connecting their dependencies, allowing the developer to focus on business logic rather than manually managing object creation and wiring.
